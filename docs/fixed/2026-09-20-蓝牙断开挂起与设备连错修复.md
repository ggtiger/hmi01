# 蓝牙断开挂起 / macOS 设备连错 / 无解析诊断

> 日期：2026-09-20
> 现象：模块 A 显示已连接但力值 `--`；点「断开」无响应，清零/断开按钮全部灰死；扫描列表里地址全是 00:00:00:00:00:00
> 提交：本次提交

## 一、问题复现与定位

用户截图（蓝牙模块联结弹窗）分析出三个叠加问题：

1. **断开挂起**：`disconnect()` 内的 `unsubscribe()`/`disconnect()` 同样没有超时——CoreBluetooth 对无响应设备执行这些操作也会挂起 → `force_disconnect` 不返回 → 前端 busy 卡在 'A'，所有按钮 disabled
2. **macOS 地址全零**：CoreBluetooth 不暴露真实 MAC，`props.address` 恒为 `00:00:00:00:00:00`。connect 按 address 匹配设备 → **匹配到扫描列表中第一个全零设备（连错设备）**。截图中连上的 BT-31_LE_CSB 是通用蓝牙串口模块（非力值模块），所以永远没有 0xAA 力值帧 → 力值 `--`
3. **无解析诊断**：连错设备后通知数据解析失败只写 Rust 日志，前端完全看不到，用户无法判断"连上了但没数据"的原因

## 二、修复方案

`bluetooth.rs`：

1. **disconnect 重构为"先标记、后清理"**：立即置 `is_connected=false` 并取出 peripheral（通知循环自动退出）→ 推送 `force-connection-changed`（UI 即时恢复）→ 底层 unsubscribe（3s 超时）/disconnect（5s 超时）best-effort 执行，超时也放行。**断开永远快速返回，绝不挂起**
2. **设备匹配改用 `peripheral.id()`**（平台标识：macOS 为 CoreBluetooth UUID，Windows 为 MAC）——scan 返回新增 `id` 字段，connect 按 id 精确匹配，不再依赖 address
3. **解析失败诊断事件**：notification_loop 解析失败时 emit `force-debug {channel, message}`（1s 节流），message 含原始字节 hex + "可能不是力值模块"提示
4. write 套 5s 超时（`try_write` 辅助函数，含重试轮）

前端：

5. `ForceDeviceInfo` 加 `id`；`forceConnect(channel, deviceId)`；ForceModal 用 `d.id` 连接
6. 全零地址显示 `—`（`displayAddr`）
7. 通道卡在"已连接但无数据"时显示最近一条诊断信息（琥珀色提示条）
8. 扫描列表 RSSI < -80dBm 标注「信号弱」；移除无意义的全零地址展示

## 三、验证

- `cargo build` 零错误零警告；`cargo test` 17/17
- `tsc --noEmit` 零错误
- 行为：断开即时生效（<100ms UI 恢复）；连接后若设备无有效帧，通道卡显示诊断信息

## 四、教训与关联

- **CoreBluetooth 三大坑**：①不暴露 MAC（address 全零，匹配必须用 identifier）；②connect/unsubscribe/disconnect 对不可达设备全部可能无限挂起（**每个 BLE 调用都必须套 timeout**）；③全零地址还会导致按地址匹配时连错设备
- 连接成功 ≠ 数据可用：UI 需要把"无数据"的原因透出给用户（诊断事件），否则无法区分设备问题与代码问题
